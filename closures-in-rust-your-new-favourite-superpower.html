Closures in Rust

February 19, 2026 Matt Earp

You know that feeling when you discover a feature in a language and think, "Ok… Really interesting that is all just built in!" That's closures in Rust. They look simple on the surface — just little anonymous functions you can toss around — but underneath, Rust's ownership system turns them into something special. Something other mainstream languages do not quite pull off.

Let's dig in.

So What is a Closure?

If you've used JavaScript, Python, or pretty much any modern language, you've met closures before. They're functions that "close over" their environment — meaning they can reach out and grab variables from the scope they were defined in.

Here's the twist: in most languages, closures just… grab stuff. There's a garbage collector to clean up the mess later. Nobody thinks about who owns what.

Rust doesn't have a garbage collector. Rust thinks about who owns what all the time. And rather than making closures painful, this actually makes them brilliant — because the compiler figures out, at compile time, exactly how your closure interacts with the data around it. No runtime overhead. No hidden copies. No surprise mutations.

Let's see it in action.

The Three Flavours of Capture

When a closure reaches out and grabs a variable from its environment, Rust decides how to capture it based on what the closure actually does with it. There are three modes, and they map directly onto Rust's core ownership concepts:

Capture ModeWhat HappensTrait Implemented
Immutable borrow (&T)The closure peeks at the data but doesn't change itFn
Mutable borrow (&mut T)The closure modifies the data in placeFnMut
Ownership (T)The closure takes the data — the original variable is goneFnOnce

The beautiful part? You don't have to pick. Rust infers the least restrictive mode that makes your code work. You write natural, readable code, and the compiler does the rest.

Flavour 1: Borrowing Immutably 

fn main() {
    let names = vec![
        "Alice".to_string(),
        "Bob".to_string(),
        "Charlie".to_string(),
    ];

    // This closure only *reads* `names`, so Rust borrows it immutably
    let print_count = || println!("Count: {}", names.len());

    print_count();

    // `names` is still perfectly usable here — nothing was consumed!
    println!("Names still here: {}", names.len());
}
Count: 3
Names still here: 3

The closure print_count calls names.len(), which only needs a shared reference. Rust sees this and automatically captures names by &T — an immutable borrow. The closure implements the Fn trait, meaning you can call it as many times as you like, and names remains completely untouched and usable afterwards.

In a language like JavaScript, you'd never even think about this. But you'd also never get the guarantee that this closure can't mutate your data behind your back. Rust gives you that guarantee at zero cost.

Flavour 2: Borrowing Mutably

fn main() {
    let mut scores = vec![10, 20, 30];

    // This closure *modifies* `scores`, so Rust borrows it mutably
    let mut add_score = || scores.push(40);

    add_score();

    println!("Scores after mutation: {:?}", scores);
}
Scores after mutation: [10, 20, 30, 40]

Now we're pushing to the vector, which requires &mut self. Rust automatically upgrades the capture to a mutable borrow (&mut T). Notice two things:

  1. The closure itself must be declared let mut add_score — because calling it mutates state, so the binding to the closure needs to be mutable too. Rust makes the mutation visible in the code. No sneaky side effects hiding behind an innocent-looking variable.

  2. You can't use scores while the mutable borrow is active. Try inserting a println!("{:?}", scores) between the closure definition and the call, and the compiler will politely refuse. This is Rust's borrowing rule — one mutable reference at a time — and it applies to closures exactly the same way it applies everywhere else. Consistency is king.

Flavour 3: Taking Ownership 

Sometimes a closure needs to own its data outright. This happens most often when the closure outlives the scope it was created in — think spawning a thread or returning a closure from a function. That's where the move keyword comes in.

But ownership transfer also happens naturally with iterators:

fn main() {
    let data = vec![1, 2, 3, 4, 5];

    // `into_iter()` consumes `data`, transferring ownership into the iterator chain
    let doubled: Vec<i32> = data.into_iter().map(|x| x * 2).collect();

    // `data` is gone — uncomment the next line and the compiler will stop you:
    // println!("{:?}", data);  // ERROR: value used after move

    println!("Doubled: {:?}", doubled);
}
Doubled: [2, 4, 6, 8, 10]

Here, into_iter() consumes the vector, and the closure |x| x * 2 receives each element by value. The original data is gone. This isn't a runtime error waiting to happen — the compiler catches it before your code ever runs.

Try doing that in Python. You'd get a valid but empty list, or worse, a subtle bug. In Rust, misuse of moved data is a compile-time impossibility.

The move Keyword: Forcing Ownership

Sometimes Rust's inference picks an immutable borrow, but you need the closure to own the data — typically because you're sending it to another thread. That's when you reach for move:

use std::thread;

fn main() {
    let greeting = String::from("Hello from the other side!");

    // Without `move`, this won't compile — the thread might outlive `greeting`
    let handle = thread::spawn(move || {
        println!("{greeting}");
    });

    // `greeting` has been moved into the closure — it's no longer available here
    // println!("{greeting}");  // ERROR: value used after move

    handle.join().unwrap();
}
The move keyword tells Rust: "I don't care what the closure needs — give it ownership of everything it captures." This is essential for thread safety, because Rust's type system requires that data sent across threads is Send, and a dangling reference definitely isn't.

This is where Rust truly separates itself from the pack. In Go for example, you can accidentally share a pointer across goroutines and get a data race. In Java, you're relying on synchronized blocks and hoping for the best. In Rust, data races involving closures are a compile-time error. Full stop.

Closures + Iterators 

If closures are a bit like a Rust superpower, iterators are the hero's cape. Together, they let you write expressive, functional-style transformations that compile down to code as fast as a hand-written for loop (seriously — Rust calls these "zero-cost abstractions" and they mean it).

fn main() {
    let words = vec!["hello", "world", "from", "rust"];

    // Chain closures together for expressive data pipelines
    let shout: Vec<String> = words
        .iter()                          // borrow each element
        .filter(|w| w.len() > 4)         // keep only words longer than 4 chars
        .map(|w| w.to_uppercase())        // transform to uppercase
        .collect();                       // gather into a new Vec

    println!("Shouting: {:?}", shout);
    println!("Original words still here: {:?}", words);
}
Shouting: ["HELLO", "WORLD"]
Original words still here: ["hello", "world", "from", "rust"]

Every closure in that chain borrows immutably, so words survives unscathed. The compiler knows this. You know this. And the generated machine code is identical to what you'd get from a hand-optimised loop — no heap allocations for intermediate collections, no virtual dispatch, no garbage collection pauses.

Compare this to Java's streams or C#'s LINQ. Those are lovely APIs, but they carry runtime overhead from boxing, dynamic dispatch, and garbage collection. Rust gives you the same ergonomics with none of the cost.

What exactly sets Rust apart here?

Zero-cost abstraction. Closures in Rust are monomorphised at compile time. Each closure gets its own unique, anonymous type. The compiler can inline them aggressively. There is no Function object on a heap somewhere — it's all flattened into tight machine code.

Ownership is explicit. In JavaScript, a closure can silently keep a massive object alive because it captured one tiny field. Memory leaks from accidental closure captures are a real and common problem. In Rust, if a closure owns data, you know it owns data, because the original variable becomes unusable.

Concurrency safety is guaranteed. Closures that cross thread boundaries must satisfy Send and Sync. The compiler enforces this. You literally cannot write a data race with safe Rust closures. This isn't a convention or a best practice — it's a mathematical guarantee enforced by the type system.

The trait system is elegant. Fn, FnMut, and FnOnce form a clear hierarchy. If a function accepts FnOnce, you can pass any closure. If it requires Fn, your closure must be pure enough to call repeatedly without side effects. This gives API designers fine-grained control over what callers can do, expressed entirely through types.

Which Trait Does Your Closure Implement?

FnOnce  ⊇  FnMut  ⊇  Fn

- Every closure implements FnOnce (it can be called at least once)
- If it doesn't move out of captured data, it also implements FnMut
- If it doesn't mutate captured data, it also implements Fn

Think of it as a ladder of increasing flexibility. Fn closures are the most reusable — you can call them from multiple threads, pass them around freely, call them a thousand times. FnOnce closures are the most powerful — they can consume their captures, but only once.

Closing observations

Closures are one of those features that every language has, but Rust's implementation is in a class of its own. The combination of zero-cost abstraction, compile-time ownership tracking, and the Fn trait hierarchy means you get expressiveness that rivals functional languages and performance that rivals C — simultaneously.

If you're new to Rust, closures are where things start to "click." You'll find them everywhere: in iterator chains, in error handling with unwrap_or_else, in thread spawning, in async runtimes, in builder patterns. Master closures and you've unlocked a huge chunk of idiomatic Rust.
